## 1. Problem restatement

Patient effort is generated by an independent neural oscillator and is supposed
to trigger an assisted breath when it crosses the vent's trigger sensitivity.
Today, whether an effort is even *considered* depends on a phase accident:

- **Phase-accident gate (the bug).** `_advanceNeural()` latches
  `pendingPatientTrigger` **only** at the single tick of neural-cycle rollover,
  and **only if** the machine is in `Phase.EXPIRATION` at that exact instant
  (`js/simulation.js:352-354`). The actual threshold check
  (`_maybeTriggerFromPatientEffort`, `js/simulation.js:360-388`) then early-returns
  unless `pendingPatientTrigger` is set (`:361`). So an effort whose onset tick
  lands during machine `INSPIRATION`/`HOLD` can never be rewarded in that neural
  cycle, even though `Pmus` stays active for a full `neuralTi` afterward and the
  machine may open the exhalation valve milliseconds later.

- **Silent drop (no marker).** `_resolvePendingPatientTrigger`
  (`js/simulation.js:395-407`) records a `'failed'` event in exactly one narrow
  path: pending **was** set in expiration but neural inspiration ended before
  threshold was crossed (`:403-405`). The two high-volume drop classes are NOT
  recorded:
  1. onset during `INSPIRATION`/`HOLD` → pending never set → `:396` returns, no
     event;
  2. pending set in expiration but a new machine breath starts before threshold →
     `:398-400` clears pending and returns *before* the `'failed'` record at
     `:405`.
  Both vanish from `triggerEvents` and from the breath counters. The patient
  "fought the vent" and the simulator shows nothing.

- **Sliding cliff (sweep-confirmed).** The throwaway harness
  (`scratch/trigger-sweep.mjs`, real engine, 60 s/cell) shows the breakdown rate
  is not fixed — it slides with the machine's inspiratory dead-window:

  | Condition | Clean 1:1 up to | Cliff (first material drop) |
  | --- | --- | --- |
  | VC-CMV, I:E 1:2, no hold | RR 28 | **~RR 30** |
  | VC-CMV, I:E 1:1 | RR 20 | **~RR 22** |
  | VC-CMV, hold 0.5 s | RR 22 | **~RR 24** |
  | PC-CMV, I:E 1:2 | RR 28 | **~RR 30** |

  This reconciles SME-001's "~22": that report is an **I:E 1:1 / hold** condition.
  At default I:E 1:2 the accident would not surface until ~RR 30. Above the cliff,
  the dropped efforts are silent (no `'failed'` marker), which is why SME-001/004
  read as "dyssynchrony I didn't expect."

PC-CSV is a separate story (see SME-005/006): under default *strong* effort it
tracks set rate; its single-digit-RR + apnea profile is reproduced by **trigger
insensitivity vs effort** (weak `Pmus` or stiff `Ptrig`), not the phase gate.
The fix below addresses both by making *every* unrewarded effort an explicit,
visible, counted event.

**Reclassification (decision Q7).** SME-005/006 is **correct physiology lacking a
visible cue, not a measured-RR calculation bug.** When a patient's effort cannot
cross the set trigger sensitivity, the vent correctly delivers no breath, the
measured (delivered) RR is correctly low, and apnea correctly fires — that is what
a real ventilator does. **This fix does NOT change the trigger-threshold math
(§2 gate c) or the apnea logic.** It adds *visibility* only: failed-trigger
markers, a Teaching-Mode neural/effort-rate readout, and an ineffective-effort
counter, so the learner can see *why* the delivered rate is low instead of being
surprised by it. The phase-accident drop (SME-001/004) is the only genuinely
*incorrect* behavior being corrected.

## 2. Target behavior — the eligibility rule

Replace the rollover-tick latch with a **continuous, per-tick eligibility
evaluation** while a neural inspiration is active. An effort is rewarded a breath
iff it passes three gates, evaluated every tick (not just at onset). Exactly one
outcome — `triggered` **or** `failed` — is emitted per neural inspiration.

Three gates (all must hold to deliver):

**(a) Ventilator available.** The machine is not mid-mandatory-breath. In engine
terms: `this.phase === Phase.EXPIRATION` (the machine has opened exhalation and
is willing to be re-triggered). `INSPIRATION` and `HOLD` mean the vent is busy
delivering/holding a mandatory breath and cannot honor a trigger. An effort here
resolves to the **terminal** outcome `gateFailed='ventilator_unavailable'`
(decision Q2). **HOLD is treated identically to INSPIRATION** (decision Q6): a
hold is a momentary measurement maneuver, not a ventilation mode, so an effort
during it is an ineffective effort — acceptable because a hold should not be left
engaged long enough to matter clinically.

> **Future extension point (Q2).** `ventilator_unavailable` is a single named
> terminal outcome *now*. A future branch may subdivide it into breath-stacking /
> double-triggering / reverse-triggering once those phenomena are modeled. We do
> **not** design stacking here; we only leave the seam (the `gateFailed` reason
> code) where that subdivision would attach.

**(b) Past the genuine expiratory refractory.** Defined on `phaseTime` *within
expiration*, not on the neural-rollover tick: `this.phaseTime > this.triggerLockoutSeconds`
(currently `0.10` s, `js/simulation.js:130`). This is the post-breath valve-reset
window — a real refractory, the same 100 ms the engine already uses
(`js/simulation.js:363`). The fix keeps the threshold but stops conflating "we
are in refractory" with "the effort never happened."

**(c) Effort crosses threshold.** **Unchanged from today** — the engine's
existing physiology stays exactly as in `_maybeTriggerFromPatientEffort`
(`js/simulation.js:367-382`):
  - `pmus = this.currentPmus`
  - `elasticRecoilPressure = this.volumeAboveEq / this.lung.compliance` (this is
    the auto-PEEP / trapped-gas load the effort must overcome — preserved)
  - pressure path: `max(0, pmus - elasticRecoilPressure) >= vent.pressureTriggerCmH2O`
  - flow path: `max(0, currentFlow*60) >= vent.flowTriggerLpm`
  No change to the trigger math; only *when* and *how often* it is evaluated
  changes, plus what we record on failure.

### Pseudo-code (references real fields; not an implementation)

```
// called each tick AFTER _advanceNeural() + _computePhysics(), replacing the
// pending-latch flow in _maybeTriggerFromPatientEffort / _resolvePendingPatientTrigger
evaluatePatientTrigger():
    effortPresent = (this.patientRR > 0) && (this.vent.pMusMax > 0) && this.neuralInspActive
    if (!effortPresent):
        return                                   // NO effort → no event (passive)

    if (this.neuralCycleResolved):               // one outcome per neural insp
        return

    // Gate (a): ventilator available?
    if (this.phase !== Phase.EXPIRATION):
        // effort during mandatory INSPIRATION/HOLD → cannot be honored
        emitFailed(gateFailed = 'ventilator_unavailable')   // Pmus present, no Pvent
        this.neuralCycleResolved = true
        return

    // Gate (b): past genuine refractory?
    if (this.phaseTime <= this.triggerLockoutSeconds):
        return                                   // too soon; hold & re-check next tick
                                                 // (NOT a failure yet — effort persists)

    // Gate (c): effort crosses sensitivity? (existing math, unchanged)
    deflection = (triggerType == 'pressure')
        ? max(0, currentPmus - volumeAboveEq/lung.compliance)
        : max(0, currentFlow*60)
    threshold  = (triggerType == 'pressure') ? vent.pressureTriggerCmH2O
                                             : vent.flowTriggerLpm
    if (deflection >= threshold):
        this.scheduledBreathTrigger = 'patient'  // delivered (existing path → _startNewBreath)
        this.neuralCycleResolved = true
        return
    // else: eligible but sub-threshold this tick → keep evaluating until neural insp ends

// when neural inspiration ENDS (neuralInspActive true→false) still unresolved:
onNeuralInspirationEnd():
    if (effort was eligible (gates a,b passed at some point) but never crossed threshold):
        emitFailed(gateFailed = 'threshold')     // ineffective effort: Pmus present, no Pvent
    // reset for next cycle
    this.neuralCycleResolved = false
```

### Failure-mode table (what each gate failure means)

| Gate failed | Engine condition | Emits | Taxonomy |
| --- | --- | --- | --- |
| (a) ventilator unavailable | effort while `phase ∈ {INSPIRATION, HOLD}` (HOLD same as INSPIRATION, Q6) | **FAILED TRIGGER** `gateFailed='ventilator_unavailable'` — terminal now; future subdivision seam (Q2) | ineffective/wasted effort (vent busy) |
| (b) refractory | effort within first `triggerLockoutSeconds` of expiration | **nothing** (transient hold; effort persists and is re-checked) | n/a unless whole window is refractory (degenerate → failed) |
| (c) threshold | eligible, but deflection `<` sensitivity for the whole neural insp | **FAILED TRIGGER** `gateFailed='threshold'` | ineffective effort (sub-threshold) |
| — no effort | `pMusMax==0` or `patientRR==0` or not in neural insp | **nothing** | passive patient (correct silence) |

Key invariant the fix must satisfy: **every neural inspiration with effort
present resolves to exactly one of {delivered breath, failed event}** — never a
silent drop. Refractory is the only "no event" state and it is transient by
construction.

> **Latent defect (PR3 must close, validated by NT6).** Today's engine emits
> *phantom* `'failed'` events for a commanded **zero-effort** oscillator
> (`pMusMax 0`, `patientRR > 0`): the `simulation.js:352` latch sets
> `pendingPatientTrigger` without checking `pMusMax`, and the fizzle path then
> records a `'failed'` marker even though no effort exists. The **`effortPresent`
> gate** in §2's pseudo-code (which requires `pMusMax > 0`) must guard against
> this so the "— no effort → nothing" row above actually holds. NT6 is the
> regression check that proves it.

## 3. Failed-trigger event contract

The engine already has the right container and the right consumer; the fix
**enriches the event shape** and **widens where failed events are emitted**. No
new buffer is required.

- **Where it lives:** the existing `this.triggerEvents` list
  (`js/simulation.js:199`), appended by `_recordTriggerEvent` (`:409-416`), which
  already time-prunes to `triggerEventRetentionSeconds` (60 s). Consumed via the
  existing `getTriggerEvents(tMin, tMax)` (`:817-819`).

- **Current shape:** `{ type, time }` with `type ∈ {'machine','patient','failed'}`.

- **Proposed minimal shape (backward-compatible — keep `type` and `time`):**

  ```
  {
    time,                 // existing: globalTime of the event (keep key)
    type,                 // existing: 'machine' | 'patient' | 'failed' (keep key)
    tSec:        <number> // alias of time for readability (optional)
    gateFailed:  <string|null>,  // null for delivered; else
                                 // 'ventilator_unavailable' | 'threshold' | 'refractory'
    pmus:        <number>, // currentPmus at resolution (cmH2O) — marker height / tooltip
    phase:       <string>, // machine phase at failure: 'INSPIRATION'|'HOLD'|'EXPIRATION'
  }
  ```

  Existing tests read only `event.type` and `event.time`; both keys are retained,
  so no existing reader breaks.

- **How `waveforms.js` consumes it (already wired, needs feeding):**
  `WaveformDisplay.renderFrame` already calls `sim.getTriggerEvents(...)`
  (`js/waveforms.js:734`) and passes events into each renderer
  (`:742-744`); `_drawTriggerMarkers` already dispatches `event.type === 'failed'`
  to `_drawFailedTriggerMarker` (`js/waveforms.js:321-331`). Today that branch is
  almost never reached because failed events are barely emitted. After the fix it
  is fed for real; `gateFailed`/`pmus` can style the marker (e.g., a small "×" at
  baseline whose height tracks `pmus`, with a tooltip naming the gate). **No new
  render plumbing — just richer events.**

- **How `main.js` consumes it (counter + dual-rate readout):**
  - **Ineffective-effort counter:** add an "ineffective efforts" count for the
    teaching panel derived from
    `sim.getTriggerEvents(window).filter(e => e.type === 'failed').length`.
  - **Delivered measured RR (unchanged, both modes):** already computed from
    *delivered* breaths (`breathTimestamps` → `_updateMeasuredRR`,
    `js/simulation.js:423-449`), so it remains correct without change; the new
    failed-event trail is what explains a low delivered RR instead of leaving it
    unexplained.
  - **Teaching-Mode-only neural/effort RR (decision Q4):** in **Teaching Mode
    only**, show a *second* rate readout — the patient's neural/effort rate
    (the commanded `sim.patientRR`, or equivalently the neural-onset rate) —
    displayed alongside the existing delivered measured RR. **Standard mode is
    unchanged: delivered RR only** (the clinical monitor view). Rationale: this
    directly resolves the SME-005/006 "expected 35, saw 6" confusion — the
    learner sees both the patient's drive (e.g. 35) and what the vent actually
    delivered (e.g. 6), with the failed-effort markers between them explaining the
    gap. It is a teaching overlay, not a change to the clinical readout.

## 4. Clinical grounding (Mireles-Cabodevila taxonomy)

Patient–ventilator asynchrony has a named vocabulary. An **ineffective (failed /
wasted) effort** is a patient inspiratory effort that does **not** trigger a
machine breath — operationally, `Pmus` is present but no `Pvent` (no delivered
assist) results. It is a *diagnosable, visible* event on real ventilator
waveforms (a `Paw`/flow deflection with no breath). Our `gateFailed` reasons map
onto its common causes: `ventilator_unavailable` ≈ effort during the machine's
mandatory inspiration/refractory (timing mismatch / reverse-triggering territory);
`threshold` ≈ effort too weak for the set trigger sensitivity (or excess
auto-PEEP load). The whole point of the fix is to make the simulator agree with
the taxonomy: an ineffective effort should be **shown and counted**, never
silently dropped.

Consistent with decision Q7: a sub-threshold effort producing no breath — and the
apnea alarm that follows when efforts stay sub-threshold — is **clinically correct
behavior**, faithful to the taxonomy. The fix therefore leaves the trigger-threshold
math (§2 gate c) and the apnea logic **untouched**; it only renders the
already-correct ineffective effort visible (marker + Teaching-Mode neural rate +
counter). The sole *incorrect* behavior corrected by this work is the line-352
phase-accident drop (gate a), where an effort the vent *should* have honored was
dropped by timing coincidence.

- **Accounting closes everywhere:** for every cell, `neural onsets ==
  delivered patient breaths + failed events` (machine breaths tracked

- **No cliff for *valid* efforts:** every expiration-phase, supra-threshold effort

  physiological ceiling (neural period approaching machine `Ti + refractory`),

- **Failed efforts are counted, not silent:** drop% becomes "fail%" with a marker
  and a counter behind every one.

Acceptance gate for the engine PR: NT1–NT6 green, all existing tests green
(except a possibly-revised 28B per §5, only with Christian's sign-off), and the
accounting identity holds across the entire grid.

## Design decisions (resolved)

Decisions recorded by Christian (RT) on 2026-06-11. Original question text is
preserved under each item so the reasoning trail survives.

1. **Refractory value.** *Question:* Keep the hardcoded
   `triggerLockoutSeconds = 0.10` s as the genuine post-breath refractory, or set
   a clinically-motivated value? Is 100 ms the right valve-reset / re-trigger
   lockout for teaching?
   - **Decision (RESOLVED-for-now):** Keep `triggerLockoutSeconds = 0.10` s.
     Revisit only if a test or an SME shows it's wrong. No change in this work.

2. **Inspiration-phase efforts: ineffective vs. double-trigger.** *Question:*
   Should an effort during the machine's mandatory inspiration be shown purely as
   an *ineffective effort* (honest, simplest), or should the model eventually
   represent breath-stacking / double-triggering / reverse-triggering (more
   realistic A/C behavior)? This decides whether `ventilator_unavailable` is a
   terminal failure or a future branch point.
   - **Decision (RESOLVED):** Model it as a **terminal ineffective effort now**
     (`gateFailed='ventilator_unavailable'`), but **architect for future
     extension** — the `gateFailed` reason code is the seam where a future branch
     may subdivide into breath-stacking / double-triggering / reverse-triggering.
     **Do not design stacking now.** Reflected in §2 gate (a), the failure-mode
     table, and the "future extension point" note.

3. **PC-CSV sub-threshold → apnea.** *Question:* Today an insensitive trigger in
   PC-CSV leads to apnea (SME-005). Is "apnea when effort can't cross the trigger"
   the desired teaching outcome, or should there be a visible "effort detected,
   below trigger" cue *before* the apnea alarm — and should PC-CSV have any backup
   at all?
   - **Decision (DEFERRED to Limb 2 / PR4):** The Teaching-Mode neural-rate readout
     (Q4) plus the failed-effort markers **already provide a pre-apnea cue**, so a
     dedicated "effort below trigger" banner is **optional**. Finalize during PR4
     rendering design. Apnea logic itself is unchanged (see Q7).

4. **Two rates on the monitor?** *Question:* Should the display distinguish
   *delivered* RR from *neural/effort* RR (two numbers), so the learner sees both
   the patient's drive and what the vent actually delivered? This directly
   addresses the SME-005/006 "expected 35, saw 6" confusion.
   - **Decision (RESOLVED):** Show **both** delivered RR and neural/effort RR, but
     **only in Teaching Mode**; **standard mode shows delivered RR only** (clinical
     view). Specified in §3 (main.js consumer subsection).

5. **Marker density.** *Question:* One failed marker per ineffective effort —
   acceptable visual density at high rates, or should closely-spaced failures
   aggregate?
   - **Decision (DEFERRED to PR4):** Implementation note — **aggregate
     closely-spaced failures if visually noisy.** Decide concretely during the
     rendering limb.

6. **Hold stealing trigger opportunity.** *Question:* An inspiratory hold pulls the
   cliff to ~RR 24 because HOLD blocks triggering. Hold is a momentary maneuver,
   not a ventilation mode — should efforts during a hold be treated the same as
   during inspiration (`ventilator_unavailable`), or should the spec say holds
   shouldn't be left engaged long enough to matter?
   - **Decision (RESOLVED):** Treat efforts during **HOLD identically to
     INSPIRATION** (`gateFailed='ventilator_unavailable'`), consistent with Q2. A
     hold is a momentary measurement maneuver that should not be left engaged long
     enough to matter; this is acceptable. Reflected in §2 gate (a).

7. **Severity reclassification.** *Question:* Given the sweep, SME-005/006 looks
   like *correct physiology lacking a visible cue* rather than a measured-RR
   calculation bug. Confirm the reclassification (blocker-bug → physiology + UX)
   before PR2 encodes it as the expected behavior.
   - **Decision (RESOLVED):** Confirmed — SME-005/006 is **correct physiology
     lacking a visible cue, not a measured-RR calculation bug.** The trigger math
     and apnea logic are correct and stay unchanged; the fix adds visibility only
     (failed markers + Teaching-Mode neural rate + ineffective-effort counter).
     Reflected in §1 and §4.
